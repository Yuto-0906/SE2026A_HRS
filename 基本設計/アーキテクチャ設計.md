# ホテル予約システム アーキテクチャ設計

## 1．目的

システム分析で得られたバウンダリ，コントロール，エンティティを，Javaで実装可能な構造へ変換する。本システムはCUIを対象とせず，Webブラウザから利用者機能と受付係機能を操作できるものとする。

## 2．アーキテクチャドライバ

| 種別 | 要求 |
|---|---|
| 主機能 | 予約，自分の予約一覧確認，予約キャンセル，全予約一覧確認，チェックイン，チェックアウト |
| 開発容易性 | ユースケースごとに担当を分け，異なる担当者が並行して開発できること |
| 保守性 | Web画面の変更が予約規則やDB処理へ波及しにくいこと |
| 性能効率性 | 高性能である必要はないが，二重予約とデータ不整合を防ぐこと |
| プラットフォーム | JavaおよびJava VM環境 |
| UI | Webブラウザから操作できること |
| 永続化 | JDBCを通してHSQLDBへ永続化すること。DAO実装の交換によりMySQLなどへ変更できること |
| 再利用 | Java標準パッケージ，既存のHSQLDB JDBCドライバ，半完成コードのドメイン・DAO構造 |
| セキュリティ | 授業内のローカル実行を対象とし，インターネットへの公開は対象外とする |

## 3．採用するアーキテクチャ

### 3.1．多層アーキテクチャ

次の4層からなる多層アーキテクチャを採用する。

1. ユーザインタフェース層
   - Java標準`HttpServer`を用いてHTTP要求を受け付ける。
   - `HttpHandler`の実装クラスを，分析モデルの`<<boundary>>`に対応させる。
   - HTMLの生成とHTTP入出力だけを担当し，予約規則を持たない。
2. アプリケーション層
   - ユースケース単位のControlクラスを，分析モデルの`<<control>>`に対応させる。
   - 処理順序，トランザクション境界，例外の変換を担当する。
3. ドメイン層
   - `HotelUser`，`Room`，`Reservation`，`ReservationStatus`を置く。
   - 予約状態の遷移や予約可能条件など，システムの中心となる規則を持つ。
4. データソース層
   - DAOインタフェースを実装し，JDBCによってHSQLDBへアクセスする。
   - SQL，DB接続，行とドメインオブジェクトの変換を担当する。

依存方向は，ユーザインタフェース層からアプリケーション層，アプリケーション層からドメイン層への一方向とする。データソース層はドメイン層に置いたDAOインタフェースを実装する。これにより，ドメイン層がSQL実装へ依存することを防ぐ。

## 5．主要な設計判断

### ADR-01：Java標準HttpServerの採用

- 決定：`com.sun.net.httpserver.HttpServer`を利用する。
- 理由：Java標準パッケージの範囲でWebブラウザから操作でき，授業で扱っていない大規模フレームワークを導入せずに済む。
- 欠点：ルーティング，HTML生成，入力検証を自分で設計する必要がある。
- 対策：Handler，`RequestParameters`，`HtmlRenderer`へ責務を分離する。

### ADR-02：Web専用化

- 決定：既存CUIを完成・拡張せず，`WebServer`を起動点とする。
- 理由：ユーザがブラウザ操作を要求しており，二つのUIを保守する必要がないためである。
- 影響：既存`Form`と`CUI`は参照用として残すが，新しいControlからは依存しない。

### ADR-03：予約状態を列挙型で表現

- 決定：`ReservationStatus`へ`RESERVED`，`CHECKED_IN`，`CHECKED_OUT`，`CANCELED`を定義する。
- 理由：文字列のタイプミスを防ぎ，許可された状態遷移を明示するためである。

許可する状態遷移は次のとおりである。

```text
RESERVED -> CHECKED_IN -> CHECKED_OUT
    |
    +-> CANCELED
```

### ADR-04：空室数の重複保持を廃止

- 決定：`AVAILABLEQTY`を更新せず，部屋一覧と有効な予約から空室を求める。
- 理由：空室数と予約データが不一致になることを防ぐためである。
- 影響：既存`AvailableQty`関連クラスは新しい処理では利用しない。

### ADR-05：支払データの永続化を行わない

- 決定：宿泊料金6000円をチェックアウト画面に表示し，受付係による支払完了入力後に予約状態を更新する。
- 理由：現在の要求分析では外部決済や支払履歴の管理を要求していないためである。
- 影響：既存`Payment`関連クラスは新しい処理では利用しない。

### ADR-06：予約処理をトランザクション化

- 決定：ユーザ登録・更新，空室確認，予約登録を一つのトランザクションとして実行する。キャンセルと状態更新もトランザクション内で行う。
- 理由：途中失敗時の部分更新と，同じ部屋への二重予約を防ぐためである。

## 6．定性評価

| シナリオ | 評価 |
|---|---|
| Web画面のレイアウトを変更する | `app.web`内の変更に限定され，Control，Domain，DAOへ影響しない |
| HSQLDBをMySQLへ変更する | DAO実装と接続設定の変更に限定される |
| 新しい予約状態を追加する | `ReservationStatus`と`Reservation`の状態遷移，関係するControlを変更する |
| キャンセル機能を追加する | 独立したHandlerとControlを追加し，既存予約機能への変更を局所化できる |
| ユースケースを担当者別に実装する | HandlerとControlがユースケース単位に分割されているため並行開発できる |
| 同じ宿泊日・部屋へ同時に予約する | トランザクションとDB制約によって一方だけを成功させる |

## 7．パッケージ設計原則の評価

| 原則 | 評価 |
|---|---|
| CCP | UI変更，業務規則変更，DB変更を異なるパッケージへ分離している |
| CRP | 各パッケージを同じ責務のクラス群で構成している |
| ADP | パッケージ間依存を`web -> application -> domain`の非循環構造にする |
| SDP | 変更されやすいWeb層が，より安定したアプリケーション層とドメイン層へ依存する |
| SAP | DAOインタフェースを安定側に置き，具象SQL実装への依存を避ける |

## 8．実装前レビュー事項

- 全ユースケースに対応するHandlerとControlが存在すること。
- `Reservation`がユーザと部屋を必ず参照すること。
- 全属性，引数，戻り値にJavaの型を定義すること。
- 関連の方向と多重度を設計レベルクラス図に示すこと。
- HandlerがDAOを直接呼ばないこと。
- ControlがHTMLを生成しないこと。
- SQL実装以外からJDBC APIを直接利用しないこと。
- 予約，キャンセル，チェックイン，チェックアウトの例外系列をシーケンス図に反映すること。
